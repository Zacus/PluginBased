# Multilingual UI Support Design

## Goal

Add first-class multilingual support to the Qt 6/QML plugin host using Qt's native translation workflow. The first supported languages are English and Simplified Chinese.

The application uses English as the default language. On startup, the app reads the configured language from the existing INI configuration. If no language has been saved, it applies `en_US`. When the user changes language in the UI, the selection is persisted and reused on the next launch.

## Scope

In scope:

- Host application QML text in `app/qml/`.
- User-visible host C++ text that is exposed to QML.
- User-visible plugin card text returned by plugin interfaces.
- User-visible QML/C++ text in bundled plugins, starting with `PlayPlugin` and `DummyPlugin`.
- CMake translation build integration for `.ts` and `.qm` files.
- Runtime language switching from QML.

Out of scope for the first implementation:

- Translating internal logs, test assertion strings, and packaging/deployment script output.
- Replacing Qt Linguist with custom JSON language packs.
- Adding locale-specific formatting for dates, numbers, or currencies.
- Process-isolated plugin translation loading. Plugins still run in the current in-process model.

## Architecture

Add an application-level language service, `AppLanguageService`, under `app/`.

Responsibilities:

- Own the active `QTranslator` instances.
- Expose the current language code.
- Load translation resources for the host and bundled plugins.
- Persist language changes through `AppConfig`.
- Emit a change signal when the language changes.

`AppController` remains the QML-facing singleton. It exposes:

- `currentLanguage`
- `availableLanguages`
- `setLanguage(QString languageCode)`

QML does not talk to `AppLanguageService` directly. This keeps the public QML API centered on the existing controller singleton.

Ownership model:

- `AppLanguageService` is an app singleton with process lifetime.
- It owns `QTranslator` objects as values or private members.
- Translators are installed on `QCoreApplication` after `AppConfig::load()` and before QML is loaded.
- On language change, old translators are removed before new translators are installed.

## Translation Workflow

Use Qt Linguist.

Source language:

- English source strings in QML and C++.
- English is the fallback and default runtime language.

Translation files:

- `translations/pluginbased_zh_CN.ts`

Generated runtime files:

- `pluginbased_zh_CN.qm`

CMake integrates translation generation with Qt translation helpers. The generated `.qm` files are either embedded as resources or installed/copied with the app in a predictable translations location. Embedding is preferred for the first version because it avoids packaging path drift.

## Runtime Behavior

Startup:

1. `AppConfig::load()` reads the INI file.
2. `AppLanguageService` reads `language`.
3. If the configured value is empty or unsupported, `en_US` is applied.
4. The QML engine is created after the language is applied.

Language switching:

1. User selects a language from the toolbar control.
2. QML calls `AppController.setLanguage(code)`.
3. The language service validates the code.
4. Translators are replaced.
5. The selected code is saved to config.
6. `currentLanguageChanged` is emitted.
7. QML bindings depending on `AppController.currentLanguage` reevaluate.

For QML text, each binding should include the language dependency where needed:

```qml
text: AppController.currentLanguage, qsTr("Installed plugins")
```

This forces reevaluation when the translator changes.

## UI Changes

Add a compact language selector to the top toolbar near the theme toggle.

Initial options:

- `EN`
- `中文`

The control should use the existing visual language from `QuickUI.Components` where possible. If no matching component exists, use a small `ComboBox` or segmented-style control with restrained styling matching the existing toolbar.

## Plugin Text

Current plugin interface methods return translated display strings directly:

- `description()`
- `cardName()`

For the in-process plugin model, these can use `QObject::tr()` or `QCoreApplication::translate()` inside each plugin implementation. The host already queries these values dynamically from QML through `PluginManager`, so the model can notify `pluginsChanged` after language changes to refresh plugin cards.

Plugin metadata JSON remains validation metadata for this first version. It is not the source of localized display strings.

## Error Handling

Unsupported language code:

- Reject the change.
- Keep the existing active language.
- Log a warning.

Missing translation resource:

- Fall back to English.
- Log the missing resource.
- Keep the app usable.

Invalid or stale config value:

- Fall back to `en_US`.
- Save behavior can remain lazy until the user explicitly changes language.

## Testing

Add focused checks where practical:

- `AppConfig` persists and reads `language`.
- `AppLanguageService` rejects unsupported language codes.
- QML-visible `currentLanguage` changes when `setLanguage()` succeeds.
- Existing CTest targets still build and pass.

Manual verification:

- Build the app.
- Launch with no language config and verify English UI.
- Switch to Chinese and verify visible host/plugin UI updates.
- Restart and verify Chinese is retained.
- Switch back to English and verify persistence.

## Implementation Notes

Keep edits scoped:

- `app/AppConfig.*`
- `app/AppController.*`
- new `app/AppLanguageService.*`
- `app/CMakeLists.txt`
- relevant QML files under `app/qml/`
- bundled plugin user-visible text
- top-level CMake translation integration
- new `translations/` files

Avoid changing generated build output or packaged artifacts directly.
